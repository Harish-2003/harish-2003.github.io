From one agent to a team

When a software team takes on a hard problem, nobody does everything alone. Architects, developers and testers each do what they're best at. A hospital works the same way, with doctors, nurses, specialists and administrators. The same idea applies to AI agents.

In Sections 1 to 3 you built single agents with tools and memory. For most use cases, one well-equipped agent is enough. But what if the problem is too big or too varied for one agent to handle well?

In this section you move from one agent to several. You'll see why one agent isn't always enough, then build the main ways of coordinating a team: a supervisor delegating to workers, agents reused as tools, swarms that hand work to each other, and graphs that route work along fixed paths. Along the way you'll learn when each pattern makes sense, and when it doesn't.

✦Think of it like this

A wedding in India. One person can't book the hall, manage the caterer, handle the decorators, coordinate the mehendi artist and greet 500 guests. So there's a wedding planner (the coordinator) and specialists who each own one job. The planner doesn't cook; the caterer doesn't decorate. Multi-agent systems are built on exactly this division of labour.

4.1

When one agent isn't enough

Before the patterns, the why: when should several agents work together instead of one super-agent doing everything?

The problem with single agents

Imagine asking one agent to research the latest AI trends, analyse competitors' pricing, write a technical specification, generate the code, review that code for security issues, and build a presentation for executives. That's a lot to ask. These are the warning signs that one agent is carrying too much:

Context overload

It tries to track too many different tasks at once and loses focus, the you met in Section 3.

Jack of all trades, master of none

Results are mediocre across every task instead of excellent and accurate in specific areas.

No parallelisation

Everything happens one step after another, even when tasks could run at the same time.

Hard to debug

When something goes wrong, it's hard to pinpoint which part of the process failed.

The multi-agent solution

Picture a busy restaurant. One person could take orders, cook, serve and wash up, but it would be slow. Instead there's a host, servers, chefs and dishwashers, each focused on what they do best. Together they deliver a smooth experience.

Multi-agent systems work the same way. Instead of one very complex agent, you build several specialised agents that cooperate. Under the hood, a coordinator agent receives the request, breaks it into subtasks, and delegates each one to the right specialist. The specialists do their work and report back, and the coordinator stitches the results into one response.

Benefits of the multi-agent approach

  1. 1

    Specialisation

    Each agent becomes an expert in its domain, with a focused prompt and the right tools.

  2. 2

    Parallel processing

    Independent tasks run at the same time, saving time.

  3. 3

    Better debugging

    You can isolate and fix problems in one specific agent.

  4. 4

    Scalability

    Add new agents as the system grows, without rewriting everything.

4.2

What are multi-agent patterns?

A is a structured way of organising several AI agents to work towards a common goal.

Think of an orchestra: strings, brass, woodwind and percussion each play their part, together, under a conductor. And just as music can be organised in different ways (a small chamber group, a large symphony, a jazz band that improvises), there are different patterns for organising agents. Each solves a particular kind of problem, and choosing the right one makes your system faster and easier to build.

Every multi-agent design answers four questions:

AspectThe questionTwo ends of the spectrum
OrchestrationHow will information flow between agents?A central coordinator (a conductor) ↔ agents talking directly (a jazz group)
SpecialisationWhat is each agent's focused role and toolset?One narrow job per agent ↔ broader generalists
CollaborationHow do agents share information and build on each other's work?Output of one becomes input of the next ↔ ongoing discussion
CoordinationWho decides the order of work?A workflow you define (a classical score) ↔ agents figure it out (improvisation)

These four aspects underpin every pattern ahead. We start with the simplest and most common one.

4.3

Lab: the supervisor–worker pattern

Your first multi-agent pattern, and the most common one in production. One agent coordinates; specialist agents do the work.

In the pattern, one agent acts as the coordinator. It receives the request, decides which specialists to call, delegates the work, and combines their results into one response. The workers focus on their tasks and report back to the supervisor.

A story in three versions

You're building a market-research assistant. An investor asks: "Should I invest in electric vehicle companies?"

  1. 1

    Version 1: one agent

    It scans recent news, analyses stock performance, checks social media sentiment, reads analyst reports and compares competitors. About five minutes per question. Fine for a few questions a day. Then your manager says it must handle hundreds of questions an hour.

  2. 2

    Version 2: three agents in parallel

    A news agent scans EV news, a financial agent analyses stock performance, a sentiment agent checks social media. The tasks are independent, so they run at the same time: ideally about three times faster. It works! But the investor now gets three separate answers:

News agent

"Several large automakers announced new battery plants. One EV start-up reported production delays."

Financial agent

"EV stocks are up this quarter on average. Valuations of pure-play EV makers are high; one is burning cash fast."

Sentiment agent

"Social media sentiment is mixed. Retail investors are bullish; charging infrastructure is a common worry."

The investor stares at this wall of unconnected facts and asks: "So… should I invest or not?" Each agent did its job perfectly, but nobody synthesised the information into a recommendation.

  1. 3

    Version 3: add a supervisor

    The supervisor receives the question and thinks: "This person needs news context, financial analysis and market sentiment. I have three workers for exactly those." It calls all three at once, rephrasing the question for each, then weaves their answers into one recommendation.

All three workers run at the same time. Two minutes later the supervisor has every perspective and answers with one recommendation, something like: "The EV sector shows strong growth, but valuations are high and some companies face production problems. Established makers look steadier than newer entrants. With a high risk tolerance the sector looks promising; if you prefer stability, wait for valuations to settle." One coherent answer, and the investor can decide.

Workers stay independent

The news agent doesn't care what the financial agent is doing. Each focuses on its expertise and reports back.

Debugging is straightforward

Wrong financial data? Check the financial agent. Old news? Check the news agent. The supervisor handles synthesis, not domain logic, so bugs stay isolated.

New skills are easy to add

Need regulatory analysis? Create a regulatory agent and tell the supervisor about it. Existing workers don't change.

    def _num(value, money=False, pct=False):
    """Format numbers safely — Yahoo sometimes leaves fields empty."""
    if not isinstance(value, (int, float)):
        return "N/A"
    if pct:
        return f"{value * 100:.2f}%"
    return f"${value:,.2f}" if money else f"{value:,.2f}"


@tool
def get_stock_price(symbol: str) -> str:
    """Get the current stock price and key metrics using Yahoo Finance.

    Args:
        symbol: Stock ticker symbol (e.g., 'AAPL', 'TSLA', 'MSFT')
    """
    try:
        info = yf.Ticker(symbol).info
        return (
            f"Stock: {symbol}\n"
            f"Current Price: {_num(info.get('currentPrice') or info.get('regularMarketPrice'), money=True)}\n"
            f"Market Cap: {_num(info.get('marketCap'), money=True)}\n"
            f"P/E Ratio: {_num(info.get('trailingPE'))}\n"
            f"52 Week High: {_num(info.get('fiftyTwoWeekHigh'), money=True)}\n"
            f"52 Week Low: {_num(info.get('fiftyTwoWeekLow'), money=True)}\n"
            f"Average Volume: {_num(info.get('averageVolume'))}\n"
            f"Sector: {info.get('sector', 'N/A')}\n"
            f"Industry: {info.get('industry', 'N/A')}"
        )
    except Exception as e:
        return f"Error fetching stock data for {symbol}: {e}"


@tool
def get_stock_history(symbol: str, period: str = "1mo") -> str:
    """Get historical stock price data.

    Args:
        symbol: Stock ticker symbol (e.g., 'AAPL', 'TSLA')
        period: One of 1d, 5d, 1mo, 3mo, 6mo, 1y, 2y, 5y, 10y, ytd, max
    """
    try:
        hist = yf.Ticker(symbol).history(period=period)
        if hist.empty:
            return f"No historical data available for {symbol}"
        start_price = hist["Close"].iloc[0]
        end_price = hist["Close"].iloc[-1]
        change_pct = (end_price - start_price) / start_price * 100
        return (
            f"Historical Data for {symbol} ({period}):\n"
            f"Starting Price: ${start_price:.2f}\n"
            f"Ending Price: ${end_price:.2f}\n"
            f"Change: {change_pct:+.2f}%\n"
            f"Highest: ${hist['High'].max():.2f}\n"
            f"Lowest: ${hist['Low'].min():.2f}\n"
            f"Average Volume: {hist['Volume'].mean():,.0f}\n\n"
            f"Recent 5-day trend:\n{hist[['Close', 'Volume']].tail().to_string()}"
        )
    except Exception as e:
        return f"Error fetching historical data for {symbol}: {e}"

    ArgumentWhat it does here
    nameBecomes the tool name the supervisor sees: letters, digits, underscores or hyphens, like news_agent.
    descriptionBecomes the tool description: how the supervisor knows when to call this worker.
    system_promptThe worker's job description, with concrete instructions about which tools to use and how.
    toolsEach worker gets only the tools for its speciality. News and sentiment share Tavily search; finance gets the Yahoo Finance tools.

    The supervisor agent

    cell 8
    supervisor = Agent(
    name="research_supervisor",
    model=model,
    system_prompt="""You are a market research coordinator. When asked about investment opportunities:

1. Work out what information is needed
2. Delegate to the specialist agents:
   - news_agent: recent developments and industry news
   - financial_agent: financial metrics and performance data
   - sentiment_agent: market sentiment and investor opinions
3. Synthesize their responses into one balanced recommendation

This is educational analysis, not financial advice — say so briefly at the end.""",
    tools=[news_agent.as_tool(), financial_agent.as_tool(), sentiment_agent.as_tool()],
)
print("✓ Supervisor created")

    agent.as_tool() wraps a worker so the supervisor can call it like any other tool. (Passing the agents directly in tools=[...] does the same thing; you'll see that in the next lab.) By default each call starts the worker from a clean slate, so one question's research doesn't leak into the next. The supervisor's prompt tells it how to delegate and how to synthesise, and it ends with a guardrail: this is education, not financial advice.

    The trade-offs of supervisor–worker

    1. 1

      The supervisor is a

      Every decision flows through one agent. In production you address this with (run several supervisor instances), caching (repeated questions return instantly) and . For high volume, add load balancing and asynchronous processing.

    2. 2

      It's a

      If the supervisor crashes, the system stops. You need health checks, automatic restarts, and checkpoint management so the supervisor resumes from its last known state. For critical systems, run redundant supervisors with a mechanism.

    3. 3

      Workers can't collaborate directly

      If the sentiment agent discovers something the financial agent should know, it has to go through the supervisor. That's fine for simple workflows; for real negotiation you need collaborative communication, covered in 4.6.

    iWhy it's still the favourite

    Most multi-agent systems don't need complex negotiation. They need clear accountability, simple communication and easy debugging. That's why supervisor–worker is the most common pattern in production.

    4.4

    Lab: make agents reusable with "agent as tool"

    Build a specialist once, give it a clear description, and any other agent can discover and call it like an ordinary tool.

    Supervisor–worker works well, but if every specialist is built from scratch for one particular supervisor, you rebuild it again and again. The pattern fixes that: you wrap an agent with a description of what it does, and other agents can call it just like a regular tool. Treating components as modular, reusable tools lets a system grow without rigid dependencies between its parts.

    When an agent receives a task, it reads the available tool descriptions and picks the right one, exactly as you saw with tools in Section 2. The only difference is that these tools are agents.

    ✦Think of it like this

    A hospital's specialist doctors. The cardiologist isn't hired by one GP; any doctor in the hospital can refer a patient to them. The referral desk only needs to know "cardiologist: heart problems". Build the specialist once, and every department can use them.

    Students ask about different subjects, and you have specialist tutors for math, writing and science. Instead of writing routing logic like "if the question contains 'equation', call the math tutor", you wrap each specialist as a tool and let the teacher agent decide which one to use.

    How data flows through a team of agents

    You've built two patterns. Now zoom out and follow one request as it moves through a multi-agent system, step by step.

    The request: "What's the best laptop for video editing under ₹1,80,000?"

    Step through

    Follow the laptop question

    Pick step 1.
    1. 1

      The request arrives

      The question enters the system as raw text. Nothing has happened yet.

    2. 2

      The router makes decisions

      It reads the question and thinks: "This person needs product recommendations, price comparisons and technical specs. I know which agents can help."     3. 3

      The agents do their thing

      All three work at the same time: one works out requirements, one searches retailer listings, one reads thousands of reviews.     4. 4

      Agents talk to each other (sometimes)

      The price agent finds a laptop at ₹1,65,000, but the specs agent realises it doesn't have enough RAM for 4K. (In a strict supervisor–worker setup this exchange goes through the supervisor; in collaborative setups, covered next, agents talk directly.)

    5. 5

      Results are combined

      An aggregator (often the supervisor) collects: specs agent: "At least 32 GB RAM, a recent mid-range dedicated GPU and a fast multi-core CPU." Price agent: "Three laptops match: ₹1,72,000, ₹1,79,000 and ₹1,86,000." Review agent: "The ₹1,79,000 one is rated 4.5 stars, with praise for rendering speed."

    A single agent would have to know video-editing requirements, search several retailers, analyse reviews and synthesise everything itself: slower, more expensive and more likely to miss something. With several agents, each is an expert in its area, and they work in parallel. That raises the obvious next questions: how do agents share information, and how do you decide whether they work in sequence, in parallel or together?

    4.6

    How agents talk to each other

    Agents working in isolation aren't a system; they're just separate programs. Communication is what turns them into a team.

    Agents communicate in three main ways. Each solves a different problem and fits a different situation.

    Sequential communication

    Think of writing a research paper. You can't write the conclusion before the research, and you can't edit what hasn't been written. Some things must happen in order. In communication, one agent finishes and hands its results to the next.

    The research agent might spend 10 minutes gathering information, the writing agent 15 minutes drafting, and the editing agent 5 minutes polishing: 30 minutes in total. The writing agent literally cannot start without the research, and the editor needs a complete draft.

    +Use it when

    There are real dependencies: step B needs step A's output. Bonus: only one agent calls the LLM at a time, which helps if your account has API .

    −The cost

    Time adds up with no overlap. And if the writing agent fails after 10 minutes of research, that time is wasted: everything downstream stops and the pipeline has to restart.

    Parallel communication

    Now picture planning a conference: one person books the venue, another arranges catering, a third handles marketing. None depends on the others, so they happen at the same time. In communication, several agents work simultaneously on different parts of a problem, and their results are combined when all have finished.

    Say you're analysing a market before a product launch and need three kinds of analysis. One agent scrapes a competitor's website and builds a pricing matrix (5 minutes). Another reads thousands of customer reviews of similar products, finding patterns in complaints and praise (5 minutes). A third analyses search trends, social media mentions and industry reports (5 minutes). Run them one after another and you wait 15 minutes; run them in parallel and you wait 5, the time of the slowest agent.

    Parallel works best when tasks are independent: agent 1 doesn't need agent 2's results. It's also useful for accuracy, with several agents checking the same thing from different angles.

    Parallel for accuracy: let agents vote

    Imagine a content-moderation system. Three agents independently check whether a post breaks community guidelines. Agent 1 says safe, agent 2 says safe, agent 3 says unsafe. Two of three vote safe, so the post is approved.

    Agents make mistakes, but if they're independent they don't all make the same mistakes. If two of three agree, you can trust the result more than any single opinion; if all three flag something, you can be very confident it needs review. The maths backs this up: if each agent is wrong 5% of the time, independently, a majority vote of five agents is wrong only about 0.12% of the time, because at least three would have to be wrong together.

    If every agent uses the same model, the same data source and the same reasoning, they'll make the same mistakes and voting adds nothing. You need diversity: different models, different data sources, different approaches.

    Collaborative communication

    Think about designing a building. The architect proposes a design; the structural engineer says it won't bear the load; the architect adjusts; the interior designer suggests changes for better flow. They go back and forth until the design satisfies every constraint. In communication, agents talk to each other, share insights, negotiate trade-offs and refine their work together.

    Here three agents review code: a developer agent wrote a function that processes user data, a security agent checks for vulnerabilities, and a performance agent makes sure it's fast enough. Step through their negotiation:

      This back-and-forth doesn't happen in sequential or parallel setups. Sequential passes information one way; parallel agents work without talking. Collaboration is a real conversation that continues until the solution satisfies every agent's requirements, here balancing security, performance and maintainability. And it does work better on hard problems: experiments with multi-agent discussion show that iterative debate catches errors and explores alternatives a single agent would miss.

      +Use it when

      Agents must balance trade-offs with no single right answer: security vs performance, cost vs quality, speed vs accuracy. Decisions where one agent's recommendation affects another's.

      −The cost

      Several rounds of discussion means several rounds of LLM calls. One agent might answer in 10 seconds; three collaborating might take 30 to 40. It's slower, costlier, and harder to troubleshoot: finding which round introduced a bad decision takes more work than debugging a simple pipeline.

      TechniqueInformation flowsTimeBest for
      SequentialOne direction, A → B → CSum of all stepsReal dependencies; tight rate limits
      ParallelOut to everyone, then combinedThe slowest stepIndependent tasks; accuracy through voting
      CollaborativeBack and forth, in roundsSeveral rounds of callsTrade-offs with no single right answer

      Sequential, parallel and collaborative are the building blocks. Next you'll see how whole systems are organised around them.

      4.7

      Common orchestration patterns

      Supervisor–worker is the pattern most organisations use, but it isn't the only one. Two more solve very different problems: swarms and graphs.

      Each uses the communication building blocks you just learned, arranged for a specific kind of problem. A swarm lets agents decide who goes next; a graph makes you decide, in code, ahead of time. We cover the swarm (notebook 04) before the graph (notebook 03) because the graph is easiest to understand by contrast; you can run the two notebooks in either order.

      Swarm: agents hand work to each other

      A builds a whole system out of collaborative communication. The hard part of collaboration is coordination: who talks to whom, when, and how do you stop agents talking in circles? A swarm answers with : agents explicitly pass control to each other.

      ✦Think of it like this

      A game-design team building a stealth mission in an abandoned space station. The level designer creates the floor plan and a rough 3D . In playtesting, the game designer finds players get lost, so it goes back to the level designer, who adds landmarks and lighting. Then the narrative designer objects: bright lighting contradicts the story of a creepy, abandoned station. The level designer switches to dim emergency lights and environmental storytelling. Now the difficulty balancer finds the level too easy with clearer navigation, so back to the level designer for tougher enemy placement, without removing the visual cues. The path loops and branches based on what each specialist finds. Nobody could have predicted it up front.

      In a swarm you'd have four agents, level_designer, game_designer, narrative_designer and difficulty_balancer, each with its own expertise. There's no supervisor and no fixed sequence. When an agent finishes its part, it decides who should go next and hands off the task with context about what's been done.

        Graph: you define the paths

        The is built on a : data flows along defined paths from one node to the next. There are two flavours:

        "Isn't that what a swarm does?" The key difference: in a swarm, agents decide the path; in a graph, you define the paths up front. Before the example, the building blocks:

        Nodes

        Anything that processes data. In Strands a node can be a single agent (like a fraud-detection agent), a swarm of agents, another graph (graphs can be nested), or custom business logic: your own deterministic code wrapped as a node.

        Edges

        The connections. An edge says "when node A finishes, pass its output to node B". Edges can carry , for example "only follow this edge if the order is over $1,000".

        Dependencies

        If node B depends on node A, A must finish before B starts. The graph manages this and runs nodes in the right order. When several arrows lead into one node (like inventory check below), it runs as soon as one incoming arrow fires.

        The example: processing e-commerce orders

        Orders arrive all day. Some are small purchases from regular customers; some are big orders from brand-new accounts; some ship somewhere that doesn't match the billing address. You can't treat them all the same way.

        You could use supervisor–worker: the supervisor reads each order and decides where to send it. It works, until your payment processor asks, "How do you guarantee high-value orders always get fraud review?" With a supervisor, the routing happens inside the LLM's reasoning. You can log it, but the decision logic isn't explicit in your code.

        A graph makes the routing explicit. The risk analyser runs first; high-value orders go to manual review; suspicious ones go to fraud detection; clean, low-risk orders go straight to the inventory check. The decision tree is visible in your code, and anyone can see exactly what happens to each kind of order.

        1. 1

          High-value orders go to manual review first

        2. 2

          Suspicious orders go to advanced fraud detection

          Red flags such as a billing and shipping mismatch, or a brand-new account placing a large order.

        3. 3

          Low-risk orders from trusted customers skip the checks

          They go straight to inventory.

        4. 4

          All three paths meet at the inventory check

          In stock: shipping generates a label and the package goes out. Out of stock: refund processing notifies the customer and returns the payment. Every order ends in one of these two states.

        Directed means arrows point one way: from the risk analyser to fraud check, never backwards. Acyclic means no loops: you can't go risk analyser → fraud check → inventory → back to risk analyser, which could cycle forever. That structure guarantees every order eventually reaches an end state, shipped or refunded.

        That's why graphs are great for compliance and auditability. When your payment processor asks about fraud prevention, you point at the graph. The logic lives in code, not hidden in LLM reasoning. A large order from a new customer always follows the same path; it doesn't vary with how an LLM reads the situation that day.

        ?So where does the LLM fit?

        The graph defines the flow; each node is still an agent that uses an LLM for its task. The risk analyser understands the order in natural language, the fraud agent reasons about suspicious patterns, the inventory agent interprets stock data. You define the routing; the LLMs do the reasoning at each step.

        import re


def decision(state, node_id: str, label: str) -> str:
    """Return the value of the final 'LABEL: VALUE' line written by a node."""
    text = str(state.results.get(node_id, ""))
    matches = re.findall(rf"{label}\s*:\s*([A-Z_]+)", text.upper())
    return matches[-1] if matches else ""


def is_high_value(state):
    return decision(state, "risk_analysis", "RISK_CATEGORY") == "HIGH_VALUE"


def is_suspicious(state):
    return decision(state, "risk_analysis", "RISK_CATEGORY") == "SUSPICIOUS"


def is_low_risk(state):
    return decision(state, "risk_analysis", "RISK_CATEGORY") == "LOW_RISK"


def is_in_stock(state):
    return decision(state, "inventory_check", "STOCK_STATUS") == "IN_STOCK"


def is_out_of_stock(state):
    return decision(state, "inventory_check", "STOCK_STATUS") == "OUT_OF_STOCK"

    print(f"Status: {result.status}\nPath:   {path}")

        4.8

        When multi-agent is not the answer

        You now know supervisor–worker, swarms and graphs. Here's what doesn't get said often enough: most problems don't need multiple agents.

        It's a common story. Someone learns about multi-agent systems and immediately rebuilds a working single-agent app as five agents coordinating through a graph. The demo looks impressive. Then it goes live.

        Debugging becomes a nightmare. Which agent failed? Was it agent three's input or agent two's output? The logs show five execution paths and you're tracing which one ran. The single agent used to answer in 3 seconds; the multi-agent version takes 12 because of coordination overhead. And the error rate went up, because there are now five points of failure instead of one.

        ✦Think of it like this

        You don't hire a committee to fix a leaking tap. A good plumber with the right toolkit is faster, cheaper and easier to hold accountable. You call in a team for building a house, not for every job.

        A single agent with good tools beats a poorly designed multi-agent system. Before you design something complex, try giving one agent the right tools. Can it call your APIs? Query your databases? Run code? Read your documentation? If you structure the tools well, most problems fit in one agent's context window.

        The patterns in this section solve real problems, but they aren't default architectures. You'll know you need multiple agents when you hit actual limits:

        1. 1

          The context window keeps filling up

          You're processing thousands of documents and the agent loses track.

        2. 2

          You need true parallelism

          Waiting for three sequential 30-second API calls is too slow for your users.

        3. 3

          The expertise genuinely doesn't fit in one prompt

          The roles need such different instructions and tools that one prompt becomes a muddle.

        iThe rule of thumb

        Start with one agent, give it tools, and test it. Only add agents when one agent clearly can't cope. Three agents that work reliably beat ten that don't.
