6.0

From laptop to production

Over the last five sections you built agents that reason, use tools, remember conversations, work in teams and talk over MCP and A2A. All of it runs nicely on your laptop. Production is a different place.

The moment someone says "let's put this in front of real users", questions appear that nobody asked during development. What happens when 200 people hit your agent at the same time? What happens when the model provider has a bad day? If the agent crashes at 3 AM and nobody notices until Monday, what then?

The AI part is rarely what slows teams down. It's the infrastructure: networking, (Identity and Access Management) policies, containers, load balancers. A two-day deployment task becomes a week of troubleshooting because nobody on the team has deployed a application before, and the error messages are hard to decode.

This section closes that gap. It won't turn you into a DevOps engineer, but it gives you enough to get agents running in production. For hardened deployments with custom networking, compliance requirements or multi-region failover, you'll still want to partner with your infrastructure team.

✦Think of it like this

Cooking a great dish for your family is development. Opening a restaurant is production. The recipe is the same, but now you need a kitchen that's open on time every day, enough staff for the Friday rush, a fire extinguisher, a health inspection, a way to know when a dish went wrong, and a budget that doesn't burn the place down. This section is about the restaurant, not the recipe.

6.1

What actually changes in production

A true-to-life story first. A team built a brilliant document analysis agent. It parsed PDFs, extracted key terms and summarised findings flawlessly in development. They demoed it to leadership on Thursday, got approval on Monday, and were in trouble by Wednesday.

The agent worked great for one document at a time. In production, 200 users hit it at once. Model calls started timing out. Temporary files piled up and filled the disk. One malformed PDF crashed the whole process, and there was no recovery: just silence. No logs, no alerts, nothing. They found out it was down when a VP called to complain.

This is a normal trajectory when you skip the production-readiness conversation. Here's what changes:

Reliability isn't optional

You need error handling, retries, and , so one failure doesn't take everything down.

Security becomes real

Proper secrets management, IAM roles and network isolation replace the admin keys on your laptop.

Debugging gets harder

With many containers and interleaved requests you need structured logs, and observability. Section 7 covers this in depth; this section lays the groundwork.

Are you ready? Seven questions

Teams that rush to deploy often spend twice as long fixing things they should have handled up front. Before you go to production, answer these honestly. If most are missing, that's fine: this section and the next cover them.

6.2

Choosing a deployment path

Different agents need different homes. Here are two that look similar on paper and need completely different infrastructure.

AWS gives you four options for running agents in production: AWS Lambda, Amazon Elastic Container Service (ECS), Amazon Elastic Kubernetes Service (EKS) and Amazon Bedrock AgentCore. Each fits a different set of constraints. Picking the wrong one won't end your project, but it can cost you weeks of rework.

✦Think of it like this

Lambda is a taxi: you pay per ride, nothing is waiting between rides, and the driver forgets you when you get out. ECS is a company car: always parked outside and ready, but you pay for it all day and you maintain it. AgentCore Runtime is a hotel room: each guest gets a private room for their stay, housekeeping is included, and the room is wiped clean at checkout.

6.3

AWS Lambda: serverless and event-driven

Back to the document analysis agent. A customer uploads a contract and the agent needs to process it. You don't want a server running 24/7 waiting for uploads that might come once an hour or once a minute. You want your code to run when a document arrives, process it, and stop.

lets you attach code directly to an event. You write a handler function, connect it to a trigger (an S3 upload, an request, a scheduled event), and Lambda runs it when the trigger fires. Nothing runs, and nothing is billed, in between. That's what means: there are still servers, you just never see or manage them.

The handler, from the course code

lambda/src/app.py · setup that runs once per environment
import json
import os

from strands import Agent
from strands.models.bedrock import BedrockModel

MODEL_ID = os.environ.get("MODEL_ID") or os.environ.get("BEDROCK_MODEL_ID") or "global.anthropic.claude-sonnet-4-6"

SYSTEM_PROMPT = """You are a document analysis assistant.
When given a contract or document, you:
1. Extract key terms and parties involved
2. Flag any risky or unusual clauses
3. Provide a clear summary

Be concise and specific. Cite the exact language from the document when flagging risks."""

# Initialize the model outside the handler so it is reused across warm invocations.
# The first request pays the setup cost; later requests on the same container reuse it.
model = BedrockModel(model_id=MODEL_ID)

Notice where model is created: outside the handler, at module level. Lambda doesn't start a fresh Python process for every request. While traffic is flowing it reuses the same , and module-level objects survive between calls. The first request pays the setup cost (importing Strands, creating the Bedrock client); every later request on that environment skips straight to the handler. Move that setup inside the handler and you pay it on every single call.

lambda/src/app.py · the handler, runs on every request
def lambda_handler(event, context):
    """Handle API Gateway POST requests."""
    # Parse the request body
    if isinstance(event.get("body"), str):
        body = json.loads(event["body"])
    else:
        body = event.get("body") or event

    document_text = body.get("document_text", "")

    if not document_text:
        return {
            "statusCode": 400,
            "headers": {"Content-Type": "application/json"},
            "body": json.dumps({"error": "Missing 'document_text' in request body"}),
        }

    # A fresh Agent per request: a warm container serves many different callers,
    # so conversation history must never carry over from one request to the next.
    agent = Agent(model=model, system_prompt=SYSTEM_PROMPT, callback_handler=None)
    result = agent(f"Analyze this contract:\n\n{document_text}")

    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps({"analysis": str(result)}),
    }
  1. 1

    Parse the body

    API Gateway delivers the HTTP body as a JSON string; a direct test invocation might pass a dict. The code handles both.

  2. 2

    Validate input

    No document_text? Return a 400 with a clear error instead of sending an empty prompt to the model.

  3. 3

    A fresh Agent per request

    The model client is shared, but the agent is not. A warm environment serves many different callers, and an agent keeps its conversation in agent.messages. Reuse one agent and customer B's request would carry customer A's contract in its history. Expensive and stateless: share it. Cheap and stateful: create it per request.

  4. 4

    Return an HTTP response

    A statusCode, headers and a JSON body, which API Gateway turns into the HTTP reply.

    The architecture

    A user sends a query through API Gateway, which invokes the Lambda function. Inside, your agent sits at the centre. It calls out to the LLM for reasoning and runs tools such as clause extraction or risk scoring. The lab agent has no custom tools at all; the model does the analysis, which keeps the example small.

    Three things that will shape your design

    1. Statelessness

    Each invocation is independent. If the agent asks a clarifying question and the customer replies, that reply is a new invocation, possibly on a different environment, and the agent doesn't remember the first one. Unless you persist the conversation somewhere and restore it, your users will complain the agent has amnesia. A common fix is : store the history keyed by a session ID, load it at the start of each invocation, save it at the end.

    pattern sketch, not part of the labillustrative
    import json
import boto3
from strands import Agent

table = boto3.resource("dynamodb").Table("agent-sessions")
# model and SYSTEM_PROMPT are defined at module level, as in app.py

def lambda_handler(event, context):
    body = json.loads(event["body"])
    session_id = body["session_id"]

    # 1. Load this session's history (empty on the first turn)
    item = table.get_item(Key={"session_id": session_id}).get("Item", {})
    history = json.loads(item.get("messages", "[]"))

    # 2. Seed a fresh agent with it, then answer
    agent = Agent(model=model, system_prompt=SYSTEM_PROMPT, messages=history)
    result = agent(body["message"])

    # 3. Save the updated history for the next invocation
    table.put_item(Item={"session_id": session_id, "messages": json.dumps(agent.messages)})
    return {"statusCode": 200, "body": json.dumps({"reply": str(result)})}

    Keep an eye on size: a single DynamoDB item can hold at most 400 KB, and long conversations about long contracts can exceed it. Strands' built-in session managers (for example one that stores sessions in S3) are an alternative.

    2. Cold starts

    Monday morning, nobody has used the agent since Friday. A customer uploads a contract and waits an extra few seconds (typically 2 to 5, and up to about 15 for a large container image like this lab's) while Lambda starts a fresh environment and loads your dependencies. That's a . It happens on the first invocation and whenever Lambda scales out new environments during a spike. Container images make it slightly slower than zips. keeps a set number of environments pre-warmed, but then you're paying for idle compute, which undercuts one of Lambda's main advantages. Try it in the simulation above.

    3. The execution ceiling

    A month in, a customer uploads a 200-page contract. The agent calls the model many times, cross-references clauses and builds a detailed report. Twelve minutes in, it's still going; at 15 minutes Lambda stops the invocation. (announced at re:Invent 2025) use checkpoint-and-replay: the function reruns from the start but skips completed checkpoints, resuming where it left off. That works, but it adds complexity to your design.

    !In the lab, the real limit is 29 seconds

    The lab puts Lambda behind an API Gateway REST API, which times out after 29 seconds by default, long before Lambda's 15 minutes. Keep requests short, use a faster model (global.anthropic.claude-haiku-4-5-20251001-v1:0), or use a Lambda Function URL or AgentCore Runtime for long-running agents.

    6.4

    Amazon ECS: always-on and container-driven

    A nurse walks up to a scheduling terminal at 2 AM and types: "Is Dr. Arti available Monday for a knee replacement?" The agent checks the calendar and offers three open slots. The nurse replies: "The 9 AM slot works, patient ID is P-1234." The agent books it, confirms equipment for OR-3 and sends notifications.

    Two messages, and the second only makes sense because the agent remembers the first. This isn't a one-off either: staff use the system around the clock, and a conversation might run three, four or five messages before a procedure is booked.

    You could build this on Lambda: persist the conversation in DynamoDB, reload it on every invocation, rebuild the agent's context each time. It would work, but you'd be fighting the infrastructure instead of building the feature. A Lambda function wants to wake up, do a thing and go away. This agent needs to be awake, warmed up and ready at all times.

    (Elastic Container Service) gives you that. You put your agent in a , hand it to ECS and say "keep this running". Run it as an and it stays up. If the container crashes at 3 AM, the service notices and starts a new one. You don't get paged. You don't write recovery scripts.

    AWhat's a container?

    A container packs your code together with everything it needs to run (Python, libraries, settings) into one sealed image, like a shipping container that fits on any ship, train or truck. Build it once with docker build and it runs the same on your laptop and on AWS.

      What's actually happening on AWS

      You don't need to be a networking expert to understand the ECS deployment model. Here's what it looks like:

      A user opens a URL. That request hits an , which routes traffic only to healthy containers. Run two containers and one dies: the load balancer sends everything to the survivor while ECS starts a replacement. Users don't notice.

      Behind it, the ECS service keeps your containers running. You tell it "I want two copies of my agent running at all times", and it makes that happen. Crash? Replaced. New version? The service rolls it out gradually, keeping the old version running until the new one passes its .

      The lab runs a single task (DESIRED_COUNT=1) to keep costs down, so a crash there means a short outage until ECS replaces it; raise the count to 2 or more when you need failover.

      Each container runs from a : a config file that says "use this Docker image, give it this much CPU and memory, send its logs to CloudWatch".

      For the compute you have two options. With you specify CPU and memory and AWS handles the servers: you never see an EC2 instance, never patch an operating system, never think about capacity. With the EC2 launch type you manage the underlying instances yourself, which you'd only do for something Fargate can't provide, like a GPU. Start with Fargate; switch later if you need to.

      When to reach for Amazon ECS

      Multi-agent systems. The e-commerce order-processing graph from Section 4 had specialised agents for risk, fraud, inventory, shipping and more.       6.6

      AgentCore Runtime

      Runtime is where the agent lives and executes. Its defining feature: each user session gets its own .

      Inside that dedicated environment the agent can keep state, hold database connections and build up context across many turns. When the session ends, the whole microVM is terminated and its memory sanitised. Nothing is shared between sessions, so nothing can leak between them. In financial services, for example, an agent processing one client's portfolio has zero chance of exposing it to another client's session.

      Consider a multi-turn conversation where a user asks the agent to analyse a financial document. The agent extracts data, stores intermediate results and writes temporary files. On Lambda all of that vanishes between invocations. On ECS it lives in a shared container. On AgentCore each user gets their own sandbox, and the agent can behave as if it's running on a dedicated machine.

      Session states, and what you pay for

      When a user sends a request, AgentCore creates a session and starts a microVM. The session moves through three states: Active while the agent is processing, Idle while it waits for the next user message, and Terminated when it ends. The default idle timeout is 15 minutes: if the user goes quiet longer than that, the session ends and the microVM is cleaned up. A session can live for up to 8 hours in total; both limits are configurable.

      The cost model is what makes this attractive. Runtime bills per second for the CPU and memory your session actually consumes. While the agent is waiting (for the user, for the model's reply, for a tool), CPU usage drops to zero, so in a typical support conversation where the user takes a minute between messages you pay CPU for the 10–20 seconds of real processing per turn, not for the silence. Memory is billed for as long as the session stays open, idle time included, which is why you stop sessions you've finished with (or let the idle timeout do it). Your session state is kept throughout.

      AgentCore Gateway

      In Section 5 you built MCP servers and clients from scratch, and saw how an agent discovers and calls tools without custom integration code. That works well with a handful of servers whose tool code you write yourself.

      Most enterprises don't have MCP servers. They have hundreds of REST APIs described by specs, internal services behind authentication layers, and legacy systems nobody wants to touch. Writing an MCP wrapper for each one, with auth, error handling, retries and rate limiting, is a full-time job. And when the API team changes an endpoint or rotates credentials, you're back in the code.

      bridges that gap. Point it at an OpenAPI spec and it generates MCP tools automatically: no server code to write, no wrapper to maintain. Your agent discovers those tools exactly the way it discovered tools from your Section 5 servers, except now they come from your existing API catalogue.

      Gateway supports several backend types: an OpenAPI spec for existing REST APIs, a Lambda function for custom logic, or a remote MCP server for tools that already speak the protocol. You can combine them into a single catalogue. The agent doesn't need to know that check inventory hits a Lambda function, send notification goes through an API Gateway endpoint, and update CRM talks to Salesforce. To the agent they're all just tools.

      ✦Think of it like this

      Gateway is a universal travel adapter for your company's APIs. Each API has its own plug shape (REST, Lambda, MCP), but the agent only has one socket: MCP. Gateway converts every plug to that socket, and it also carries the right key for each door it opens.

      Authentication: inbound and outbound

      Any production deployment must answer two questions: who is allowed to call the gateway, and how does the gateway prove its identity to the APIs it calls on your behalf?

      Inbound (who can reach the gateway): pick IAM or . If your agent already runs on AWS with an IAM role (on Runtime, Lambda or ECS), IAM is the simpler path: grant that role permission to invoke the gateway and you're done. When end-user identity needs to flow through, use JWTs from Cognito, Okta or any OAuth 2.0 provider.

      Outbound (how the gateway authenticates to each API) is configured per target: an OAuth token for the internal customer API, an API key for a third-party weather service, the gateway's own IAM role for a Lambda function. (OpenAPI targets always expect an OAuth or API-key credential, which is why the lab registers a placeholder key for a free API.) The credentials are kept in secure storage (backed by AWS Secrets Manager), tokens are refreshed and cached so the gateway doesn't hammer downstream identity providers.

      The two sets of tokens are completely separate, with different scopes. A downstream API can't take the inbound token and reuse it to impersonate your agent elsewhere. Gateway handles the mechanics of authenticating to downstream APIs, but a bigger question remains: who is the user behind the request, and what are they allowed to do? That's the job of AgentCore Identity (6.9).

      AgentCore Identity

      Every production agent faces a two-sided authentication problem.

      On one side, callers must prove who they are before the agent will talk to them, whether the caller is a user, another agent or an automated workflow. On the other side, when the agent calls an external service (a CRM, a calendar API, a code repository) it needs credentials for that service. Without the first, anyone can hit your agent endpoint. Without the second, you end up embedding secrets in environment variables or hard-coding API keys, which is how breaches happen.

      Inbound: Identity supports JWT-based authorisation. Your identity provider (Amazon , Okta, Microsoft Entra ID, or any standard OAuth 2.0 / provider) issues the token, and Identity validates it before the request reaches your agent.

      Outbound: Identity manages the credentials your agent needs for external services, storing OAuth 2.0 tokens and API keys in a secure rather than in your code or configuration. Credentials are encrypted with , bound to specific agent-user combinations, and every access is logged for audit.

      Two kinds of outbound access

      In your agent code this shows up as decorators. Put @requires_access_token or @requires_api_key on a function and the SDK fetches, injects and refreshes the credential for you. Identity has built-in credential providers for services like Google, GitHub, Slack, Salesforce and Atlassian, with endpoints and provider-specific settings pre-configured; for anything else you can set up a custom OAuth 2.0 provider.

from mcp.server.fastmcp import FastMCP

# stateless_http=True: every request is independent — required on AgentCore
mcp = FastMCP("StockTools", host="0.0.0.0", stateless_http=True)


@mcp.tool()
def get_stock_price(ticker: str) -> str:
    """Get the latest stock price for a given ticker symbol (e.g. AAPL, MSFT, AMZN)."""
    try:
        stock = yf.Ticker(ticker.strip().upper())
        info = stock.info
        price = info.get("currentPrice") or info.get("regularMarketPrice")
        name = info.get("shortName", ticker.upper())
        currency = info.get("currency", "USD")
        change = info.get("regularMarketChangePercent")

        if price is None:
            return f"Could not find price for '{ticker}'. Check the ticker symbol."

        result = f"{name} ({ticker.upper()}): {currency} {price:.2f}"
        if change is not None:
            direction = "▲" if change >= 0 else "▼"
            result += f" {direction} {abs(change):.2f}%"
        return result
    except Exception as e:
        return f"Error fetching {ticker}: {e}"

      _cognito_setup() {
  if [ -z "$REGION" ] || [ -z "$COGNITO_USERNAME" ] || [ -z "$COGNITO_PASSWORD" ]; then
    echo "Error: set REGION, COGNITO_USERNAME and COGNITO_PASSWORD first." >&2
    return 1
  fi

  # User pool
  POOL_ID=$(aws cognito-idp create-user-pool \
    --pool-name "AgentCoreUserPool" \
    --policies '{"PasswordPolicy":{"MinimumLength":8}}' \
    --region "$REGION" --query 'UserPool.Id' --output text)
  [ -n "$POOL_ID" ] && [ "$POOL_ID" != "None" ] || { echo "Error: could not create the user pool." >&2; return 1; }

  # App client (public client, username/password auth)
  CLIENT_ID=$(aws cognito-idp create-user-pool-client \
    --user-pool-id "$POOL_ID" \
    --client-name "AgentCoreClient" \
    --no-generate-secret \
    --explicit-auth-flows "ALLOW_USER_PASSWORD_AUTH" "ALLOW_REFRESH_TOKEN_AUTH" \
    --region "$REGION" --query 'UserPoolClient.ClientId' --output text)
  [ -n "$CLIENT_ID" ] && [ "$CLIENT_ID" != "None" ] || { echo "Error: could not create the app client." >&2; return 1; }

  # User with a permanent password
  aws cognito-idp admin-create-user \
    --user-pool-id "$POOL_ID" --username "$COGNITO_USERNAME" \
    --region "$REGION" --message-action SUPPRESS > /dev/null || return 1
  aws cognito-idp admin-set-user-password \
    --user-pool-id "$POOL_ID" --username "$COGNITO_USERNAME" --password "$COGNITO_PASSWORD" \

      Enterprise integration patterns

      Once deployed, your agent has to talk to other systems: databases, internal APIs, third-party services, event streams. If you use AgentCore Gateway, it handles much of this (point it at a spec, get tools with auth and error handling built in). The patterns below apply on Lambda or ECS, or whenever you need behaviour Gateway doesn't cover.

      Databases

      Databases are often the first integration to break at scale. An agent serving forty concurrent users, each triggering two or three queries, will exhaust a typical Amazon Aurora (AWS's managed relational database) connection pool within minutes. sits between your agent and the database and fixes this by multiplexing hundreds of agent requests over a smaller set of real database connections. The agent code doesn't change; the infrastructure absorbs the concurrency.

      Three more rules: keep analytical queries (reports, aggregations) off your transactional database and replicate to instead; keep conversation state in DynamoDB (as in Section 3); and keep credentials in Secrets Manager with automatic rotation, not in environment variables. Scope the IAM policy to the exact secret ARN the agent needs, and keep database traffic inside a private subnet.

      External APIs

      External APIs fail in ways your agent must handle gracefully. Internal services go down during deployments. Third-party providers enforce and return 429s. Some endpoints just stop responding, with no error at all.

      The rules: set a timeout on every call; retry with ; and return a structured error the agent can reason about. "I couldn't complete the underwriting check; proceeding with a preliminary assessment" is far better than a raw 500. stop your agent burning time on timeouts when a service is clearly down. For rate-limited APIs, respect Retry-After headers, and cache responses when the data doesn't change between calls.

      pattern sketch: a resilient toolillustrative
      import random, time
import httpx
from strands import tool

FAILS, OPEN_UNTIL = 0, 0.0          # a tiny circuit breaker

@tool
def underwriting_check(applicant_id: str) -> dict:
    """Run the underwriting check for a loan applicant."""
    global FAILS, OPEN_UNTIL
    if time.time() < OPEN_UNTIL:                    # breaker open: fail fast
        return {"status": "unavailable", "detail": "Underwriting service is down; "
                "proceed with a preliminary assessment and say so."}
    for attempt in range(3):
        try:
            r = httpx.get(f"https://underwriting.internal/check/{applicant_id}", timeout=5)
            if r.status_code == 429:                   # rate limited: wait as told
                try:
                    wait = float(r.headers.get("Retry-After", 2))
                except ValueError:                     # Retry-After can also be a date
                    wait = 2
                time.sleep(wait)
                continue
            r.raise_for_status()
            FAILS = 0
            return {"status": "ok", "result": r.json()}
        except (httpx.TimeoutException, httpx.HTTPError):
            if attempt < 2:
                time.sleep(2 ** attempt + random.random())  # 1 s, then 2 s (+ jitter)
    FAILS += 1
    if FAILS >= 2:
        OPEN_UNTIL = time.time() + 30                  # stop trying for 30 s
    return {"status": "unavailable", "detail": "Underwriting check failed after 3 tries; "
            "proceed with a preliminary assessment and say so."}

A software circuit breaker does the same: after repeated failures it stops calling the broken service for a while and answers "unavailable" instantly, then tries again later.

        Event-driven integration

        Event-driven integration decouples your agent from the systems that feed it.         Industry use cases

        Here's how these patterns play out in four industries, each with different deployment requirements and integration challenges. Watch for the last line of each: the deployment fit.

        Financial services: fraud detection at transaction speed

        A bank's fraud system kept catching suspicious crypto transactions, but it flagged legitimate customers so often that "Why can't I buy Bitcoin?" became a daily support ticket. The fraud team was drowning in false positives while real fraudsters slipped through. The fraud model itself, a endpoint trained on transaction patterns, was solid. The problem was context: it saw each transaction in isolation and didn't know the customer had been making similar purchases for months.

        When a transaction arrives, the agent works sequentially: pull the customer's history from DynamoDB, feed that context to the SageMaker model alongside the current transaction, and escalate only when the risk score warrants it; high-risk transactions trigger a Lambda function that starts the investigation workflow. There's no hard-coded if risk_score > 0.8: call_lambda(): the agent reads the tool descriptions and orchestrates them based on the situation.

        →Deployment fit: AWS Lambda

        Each transaction is independent: no multi-turn conversation, no state between invocations. The agent processes one transaction, returns a decision and terminates. It scales to zero in quiet periods and to hundreds of concurrent invocations during market volatility.

        Healthcare: multi-specialty surgical scheduling

        Scheduling surgery means coordinating a surgeon, an anaesthesiologist, possibly a specialist, an available operating room, specific equipment that might be in use elsewhere, and a time the patient can actually make. A large hospital system did this manually: coordinators spent hours on the phone, checking calendars and leaving voicemails. By the time they found a slot, the patient had sometimes booked with a competitor.

        When a patient requests surgery, the agent checks the first: what kind of surgery, which specialists, which equipment. Then it queries multiple calendars in parallel to find a time when everyone is free. Once it finds a slot it books the appointments and sends SMS confirmations. It also checks equipment availability before booking and sends reminders at the right intervals, which it worked out from the tool descriptions and past scheduling patterns. You provide the tools; the model orchestrates them.

        →Deployment fit: AgentCore Runtime

        A scheduling conversation might run five messages before a procedure is confirmed, so this is a multi-turn workload. Each coordinator's conversation gets its own isolated session, and the idle timeout matches the natural pace of scheduling (a coordinator might step away to check something with a nurse). Your ECS lab runs this same scenario to teach always-on containers; with many coordinators needing private multi-turn sessions, Runtime is the better production fit.

        Manufacturing: predictive maintenance on the factory floor

        A factory had expensive CNC machines with bearings that failed without warning. One day a machine runs fine; the next it's down for three days waiting for parts. Each failure cost roughly $50,000 in lost production. Scheduled maintenance (replace bearings every six months regardless) was wasteful, and bearings still failed in between. Monitoring vibration sensors by hand produced too much data and too many false alarms.

        The agent monitors vibration sensors continuously, analyses thermal images for heat patterns, and runs everything through a SageMaker model trained to predict bearing failures. When the risk score crosses a threshold, it checks parts inventory in the warehouse database and creates a maintenance ticket automatically. It also knows to check parts before scheduling maintenance and to schedule during low-production periods, which it learned from the tool descriptions and production schedules, not from hard-coded rules.

        →Deployment fit: Amazon ECS

        This is continuous monitoring, so it runs on ECS as a long-lived service. Lambda's 15-minute limit rules it out for an agent that never stops processing sensor data, and AgentCore Runtime's per-session isolation doesn't map well to a workload with no distinct user sessions.

        E-commerce: customer support with specialised agents

        An online retailer built one agent to handle all customer support: order tracking, product recommendations and returns. It confused return policies with shipping policies, recommended out-of-stock products, and knew a little about everything without knowing enough about anything.

        The fix was three specialised agents (Order Tracking, Product Expert, Returns) wrapped as tools that an orchestrator calls: the agents-as-tools pattern from Section 4. A customer asks about returning an order; the orchestrator calls Order Tracking to check shipment status, then Returns for the policy, and combines both into one reply. Each agent focuses on what it does best, and the orchestrator also uses sentiment analysis to spot frustrated customers who need a human.

        →Deployment fit: AgentCore Runtime

        Customer support is conversational and multi-turn. Each customer's conversation gets its own isolated session, so there's no cross-customer data leakage even though the agents share tools that touch the same product catalogue and order database.

If a retry loop runs away, you'll find out on the monthly bill. If someone discovers your endpoint, nothing stops them hammering it. That's Section 7.

        When something goes wrong

        What you seeWhat it usually means and how to fix it
        AccessDeniedException when the deployed agent calls BedrockThe role is missing a Bedrock resource (often the inference-profile ARN or the region-less foundation-model ARN), or the model isn't enabled in your account. Compare with the policies in template.yaml and deploy.sh.
        Model not found / validation error on the model IDThe ID isn't exact. Copy it from Bedrock and pass it with BEDROCK_MODEL_ID.
        Lambda lab returns 504 after about 29 secondsThe API Gateway REST API timeout. Send a shorter document, use a faster model, or move to a Function URL or AgentCore Runtime.
        The first Lambda request takes 5–15 secondsA cold start. Later requests on the same environment are faster.
        sam build or deploy.sh fails straight awayDocker isn't running, the SAM CLI isn't installed, or credentials aren't set. On Windows, run the scripts from WSL or Git Bash.
        ECS: "Need at least 2 public subnets"Your default VPC's subnets don't route to an . New accounts are fine; otherwise check the route tables.
        ECS URL doesn't loadWait 2–3 minutes for health checks. Check aws logs tail /ecs/scheduling-agent.
